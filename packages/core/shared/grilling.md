# Skill: Grilling & Alignment Interview (Shared)

## When to Read This
Read and execute this skill **before** drafting implementation steps or writing code for any new feature, major architectural refactor, spike, or complex bug fix. If you cannot describe the complete boundaries, failure semantics, and acceptance verification in one sentence, you are strictly in scope.

## Context
The single most expensive failure mode in autonomous software engineering is not syntax bugs or test failures—it is writing high-quality code that answers the wrong question. When an AI agent infers human intent instead of rigorously confirming it, rework cascades across schemas, API contracts, and user expectations.

**Grilling is the mandatory alignment procedure** that closes this gap before building starts. It is an active interview discipline: relentless, depth-first, and conducted **one question at a time** until every decision branch is settled. 

In NEXUS, Grilling is not merely conversational advice; it is a **gated procedure** enforced structurally:
- Plans of type `feature`, `refactor`, `spike`, and `bug` marked `major: true` require a completed `## Grilling` section.
- Fresh plans generated by the CLI seed the marker `<!-- nexus:grilling-pending -->`.
- `nexus doctor` (check **D13**) validates that no gated work enters `in_progress` without its verified alignment record.
- In the Nexus Harness, this process is automated via the `/grill` command and the `dsh-grill-mode` package.

## Steps

### 1. Earn Your Questions (Orient First)
Before asking the human anything, execute orientation:
```bash
nexus_get_context({ task: "<task description>" })
```
Scan `.nexus/docs/index.md`, `knowledge-summary.md`, and relevant spec documents (`01_vision.md` through `08_deployment.md`).
- **Rule:** Every question whose answer is already written in the brain or codebase is a failure of preparation. Reserve human bandwidth exclusively for unresolved trade-offs and business logic.

### 2. Mirror the Ask in One Sentence
Open the interview by stating your understanding back to the human as a concrete, bounded assertion:
> *"My understanding is that we are adding [Capability] to [Component/System] so that [Target User] can [Primary Action], while preserving [Key Invariant]."*
- Do not start with a question. Give the human a concrete target to confirm or refute.
- If the human corrects your framing, refine the mirror until both sides agree on the root objective.

### 3. Decompose Decision Branches
Map the problem into five core architectural branches. Every branch that is not 100% specified is an active fork:
1. **Scope & Actors:** Who uses this? What roles or systems interact with it? What is explicitly out of scope?
2. **Data & Schema:** Does this introduce new tables, columns, or state transitions? How is backward compatibility preserved?
3. **API & Interface Contracts:** What are the endpoints, function signatures, error shapes, or UI entry points?
4. **Failure Modes & Edge Cases:** What happens during timeouts, concurrent writes, or invalid input?
5. **Provable Done:** What specific automated command or test proves this work is complete?

### 4. Conduct the Relentless Single-Question Loop
Iterate through unresolved branches following strict conversational constraints:
- **One question per message:** Never batch multiple questions into a numbered list. Batched questions receive hurried, shallow answers.
- **Provide closed choices with a recommendation:** Frame questions as discrete options rather than open-ended queries:
  > *"When an idempotency key conflict occurs, should the API: (A) (Recommended) Return the cached original response with a 200 OK and header `X-Cache: HIT`, or (B) Reject with `409 Conflict`?"*
- **Follow branches depth-first:** When an answer opens a secondary question, resolve that secondary question immediately before jumping to another branch.
- **Push back on vagueness:** "Handle it gracefully", "make it secure", or "standard behavior" are non-answers. Demand concrete operational behavior: *"If the token expires during an active upload, does it abort immediately or complete the active chunk?"*

### 5. Handle "You Decide" & Non-Technical Input
- If the user responds with *"You decide"*, *"Whatever is best"*, or leaves architectural discretion to you:
  1. Make the optimal engineering choice based on project standards.
  2. State your decision clearly to the user.
  3. Mark the decision in the record with the `[ASSUMED]` tag alongside the rationale.

### 6. Crystallize the Out-of-Scope List
Every rejected alternative and deferred feature must be recorded. The *"Out of Scope"* list is the single most valuable artifact of grilling—it prevents scope creep and stops debates that were already settled from reopening later.

### 7. Write the Alignment Record to the Plan
Open the active plan file (`.nexus/plans/<plan-id>.md`), remove the `<!-- nexus:grilling-pending -->` marker, and write the complete `## Grilling` section. 
- In the Nexus Harness, invoke the tool `finish_grilling({ record: "<markdown>" })`.

### 8. Log Architectural Surprises
If grilling surfaced a non-obvious project constraint or overturned a common assumption, record it in `.nexus/docs/knowledge.md` using `nexus_log` so future agents inherit the learning.

## Patterns We Use
- **Closed-Fork Questioning:** Formulate forks with clear trade-offs and explicit recommendations:
  - *Bad:* "How do you want to handle user sessions?"
  - *Good:* "For session storage, should we: (A) (Recommended) Store sessions in Redis with 7-day sliding TTL for instant revocation, or (B) Issue stateless signed JWTs in HttpOnly cookies?"
- **The Single-Question Rule:** Ask exactly one question per turn. Wait for user feedback before advancing.
- **The "Five Whys" of Scope:** If a requested feature seems complex or unusual, politely ask what underlying user problem motivated it before designing the architecture.
- **In-Memory Harness Alignment:** In Nexus Harness / interactive TUI modes, enter via `/grill [topic]` and utilize structured modal prompts (`ask_question` / `ask_user_question`) when available to present clean multiple-choice dialogs.

## Anti-Patterns — Never Do This
- ❌ **Do not write code before the record exists:** Code written before alignment turns the interview into an exercise in justifying existing code.
- ❌ **Do not batch questions into walls of text:** Handing the user a list of 6 numbered questions leads to cognitive overload and ambiguous answers.
- ❌ **Do not ask questions already answered in the Brain:** Never ask what database is used, what port the app runs on, or what test framework is configured when it is already in `index.md` or `package.json`.
- ❌ **Do not accept hand-waving answers:** Never accept "it should just work fast" or "do the usual thing". Pin down exact HTTP status codes, timeout thresholds, and data schemas.
- ❌ **Do not omit the Out-of-Scope section:** An alignment record without an Out-of-Scope section leaves boundaries undefined, inviting scope creep.
- ❌ **Do not skip grilling for "small" features:** If a task adds a new route or modifies database state, it has decision branches. A quick 3-question grilling takes two minutes and prevents hours of rework.
- ❌ **Do not delegate Grilling to a background subagent:** Grilling requires real-time conversational exchange with the human sponsor; it cannot be executed asynchronously by a child subagent.

## Completion Criteria
Grilling is officially complete only when all of the following conditions are satisfied:
1. **Confirmed Ask:** The human has confirmed the one-sentence problem statement.
2. **Exhausted Branches:** Every identified decision branch is either decisively resolved or explicitly assigned to the out-of-scope list.
3. **Plan Artifact Committed:** The `## Grilling` section in `.nexus/plans/<plan-id>.md` is populated, contains no pending placeholder markers, and is saved.
4. **Doctor Clearance:** Running `nexus doctor` reports no `D13` findings for the plan.

## Example

```markdown
## Grilling

**Ask:** Implement webhook event delivery with automatic exponential backoff retry for third-party developer integrations.

**Resolved Branches:**
- Delivery Semantics — At-least-once delivery. Consumers must provide idempotent webhook endpoints. Exactly-once was rejected due to distributed lock overhead.
- Retry Policy — (Recommended Option A) 5 retries with exponential backoff (10s, 1m, 5m, 30m, 2h) followed by dead-letter queue routing.
- Payload Signature — HMAC-SHA256 signature generated with the developer's webhook secret, transmitted in the `X-Nexus-Signature` header.
- Concurrency & Throttling — Webhook worker pool capped at 20 concurrent HTTP dispatches per tenant to prevent outbound port starvation.
- Persistence Layer — Webhook delivery events stored in PostgreSQL `webhook_deliveries` table with composite index on `(tenant_id, status, next_attempt_at)`.

**Assumptions & Invariants:**
- [ASSUMED] Default HTTP request timeout set to 5000ms. If a consumer endpoint hangs longer, delivery is treated as failed.
- Payload size strictly bounded to 256KB.

**Out of Scope:**
- Customer-facing dashboard UI for manual webhook replay (deferred to Phase 2).
- Mutual TLS (mTLS) client certificates.
- Custom retry schedules configured per tenant.
```

## Validation
To verify alignment compliance across the workspace:
1. Check that the active plan file contains the `## Grilling` header with non-empty content and no pending markers:
   ```bash
   grep -q "## Grilling" .nexus/plans/*.md && ! grep -q "nexus:grilling-pending" .nexus/plans/*.md
   ```
2. Run the Nexus Doctor suite to verify gate clearance:
   ```bash
   nexus doctor --strict
   ```

## Notes
- When working headlessly or in CI mode without human presence, if an urgent plan must progress, generate the `## Grilling` section with all branches explicitly labeled `[ASSUMED]`, document the exact rationale for each choice, and flag the plan for human review upon completion.
- The alignment gate keys off plan type (`feature`, `refactor`, `spike`, `major bug`), never off arbitrary task wording. Renaming a task to avoid the gate is a doctor violation.
